# Text Breakdown

A method for making a dense or difficult text genuinely understandable, one paragraph at a time, without losing the thread of the overall argument.

## Before starting

1. **Read the whole text first** (or the whole chunk being covered this batch) before writing anything. Note its structure — where it starts, where natural sections fall, roughly how long it is.

## The per-paragraph unit

For each paragraph or natural unit of the text, produce four parts, in this order:

**1. Key passage.** Quote the load-bearing sentence or phrase from the original, verbatim, in quotation marks. Keep any single quotation under 15 words if it's from a copyrighted modern source (translations of Hegel, Weber, Durkheim etc. are often still in copyright); for older/public-domain primary texts a longer quote is fine, but never quote more than one passage per paragraph unit. If the exact wording matters for the argument (a term's precise phrasing, a famous line), quote it; otherwise paraphrase and say so.

**2. Key terms.** Any word a general reader might stumble on — a technical term, a name, a piece of jargon, an untranslated foreign word — gets its own short, plain definition. Don't skip terms that seem "obvious" if they're doing real conceptual work (e.g. "real right" vs "personal right," "calling," "collective consciousness").

**3. Plain-language explanation — what the passage is actually saying, and what the author is getting at.** Two things, not one: first restate the claim in ordinary words a smart teenager would follow; then say what the author is *doing* with it — why this move, what it rules out, what it sets up for later. This second half is what keeps the breakdown from being a list of restatements.

**4. A concrete example.** One illustration from everyday life or a well-known case, THEN one example tied to the specific person's own context if it's known (their field, their project, their country/region). If nothing specific is known about the person, use one clear illustration and skip the second. Never invent personal facts about the user to make an example — use only what's actually been established.

## Stitching paragraphs into an argument, not a list

This is the part that most separates a good breakdown from a mediocre one. After every 3–5 paragraphs, or at a natural turn in the argument, add a short line marking where the argument now stands relative to what came before — "notice this is the second time he's used the same move," "this sets up the objection he answers next," "hold this against paragraph 3." The reader should feel the text accumulating toward a conclusion, not receive ten separate flashcards.

At the end of every batch, write **"End of Batch N"** followed by **"The thread so far"** — 2–4 sentences recapping the argument built across every batch so far (not just this one), and then a one-sentence preview of what the next batch covers.

At the end of the *whole text* (last batch), replace the "thread so far" with a **short numbered summary (4–6 lines)** of the entire argument start to finish, written as a cumulative story, not a list of topics.

## Simplicity calibration

Default to explaining as if to a bright, curious teenager: short sentences, no jargon left undefined, one idea per sentence. If the user has asked for something even simpler ("like I'm 12"), drop technical vocabulary further and lean harder on the examples to carry the meaning. If the user is a subject-area specialist and asks for a breakdown anyway (common for dense primary texts even among experts), keep the same four-part structure but you can let the "plain-language" part run a little denser, since the value here is organization and pacing, not just simplification.

## Handling long texts across multiple turns

- If the whole text won't fit in one batch, say so before starting, propose a natural place to break, and do the first batch.
- End each batch by naming what the next batch will cover, so the user knows what "next" or "continue" will bring.
- When the user says "next," "batch 2," "continue," or similar, proceed with the next chunk in the same format — don't re-ask what they want unless the text's structure genuinely requires a decision (e.g. several distinct chapters, unclear where to resume).
- Keep every batch self-contained enough to read on its own, but always open by grounding it in the running thread (a sentence or two, not a full recap).

## Flagging problems in the source honestly

If the text contains a claim that later scholarship has discredited (a dated scientific claim, a biased historical generalization, an argument that doesn't hold up against evidence), say so plainly in that paragraph's "what the author is getting at" section — name it, don't launder it and don't overreact to it. State what's wrong, cite briefly why (a well-known later correction or an internal inconsistency in the text's own logic), and move on. The same honesty applies to internal inconsistencies: if an author breaks a rule they set for themselves earlier in the same text, point it out when you reach it.

## After a breakdown: reading notes

If the user later asks for a "reading note," "summary," or "two-page note" covering one or more texts already broken down in the conversation, write flowing prose (not the four-part per-paragraph structure) that:
- Gives each text's core argument, its sharpest or most quotable moves, and its acknowledged weak points
- Ends with a short section connecting the texts to each other where a real connection exists (shared concept, direct disagreement, one text answering another) — never force a connection that isn't there
- Matches whatever length/format the user specifies (e.g. "two pages, 12pt Times, LaTeX") — if they ask for LaTeX or another output format, use the relevant skill/tool for that format and keep the prose itself unchanged in style from the plain-text version unless asked to shorten it to fit a page limit, in which case cut examples and secondary connections before cutting the core argument of any single text.

## What NOT to do

- Don't skip paragraphs to save time — cover the whole assigned chunk, including the "boring" transitional ones; those are often where the argument's structure actually shows.
- Don't quote more than one short passage per copyrighted source per paragraph unit, and never reproduce a long passage verbatim even if the user's uploaded text contains it in full.
- Don't front-load all the examples generically ("here's a business example, here's a farming example") — root the specific-context example in what's actually known about the person's work, not a generic version of their field.
- Don't turn the running "thread" commentary into another list — it should read like a sentence someone would actually say out loud connecting two ideas.
- Don't produce this as a downloadable file by default — deliver it inline in the chat unless the user asks for a file.
